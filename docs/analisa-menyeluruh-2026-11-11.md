## (a) Backend API + auth + RBAC + external API

### Tinggi

**A-T1. WebSocket `/ws` tidak memvalidasi user dan membocorkan semua kamera ke token apa pun.** `apps/api/app/routers/ws.py:57-77`. Auth hanya memeriksa signature JWT dan `payload["type"] == "access"`. Tidak diperiksa apakah user masih ada, masih aktif, atau login guest sudah dinonaktifkan; token embed (`role="embed"`, `sub="key:N"`) juga lolos. Snapshot berisi semua kamera aktif (id, nama, `is_online`) dikirim ke klien, dan broadcast mengirim setiap perubahan status ke semua klien tanpa filter per kamera. Dampak: guest, user tanpa akses kamera, pemegang token embed, bahkan user yang sudah dinonaktifkan bisa mengintip inventaris dan status semua kamera sampai token kedaluwarsa. Endpoint poster dan Live justru menerapkan cek akses per kamera, jadi `/ws` adalah lubang yang tidak konsisten.

**A-T2. Admin biasa bisa mengakses Live/poster/reconnect kamera apa pun tanpa grant.** `apps/api/app/core/rbac.py:258`, `apps/api/app/routers/streams.py:66`. `_check_camera_access` mengembalikan langsung untuk `role == "admin"` bila `need_playback=False`, dan `_visible_streams` mengembalikan semua stream untuk admin. Akibatnya `StreamAdminGrant.can_view` tidak ada artinya untuk Live. Catatan: kode menandai ini sebagai "perilaku lama dipertahankan" (paritas v2.0), jadi ini keputusan desain yang perlu ditinjau ulang, bukan regresi tak sengaja. Kontras: `mask_rtsp_url` membatasi RTSP ke kamera milik sendiri atau ber-grant, dan playback mewajibkan grant `can_playback`.

**A-T3. Token sesi embed tidak terikat ke kamera.** `apps/api/app/routers/external.py:192-200`. `_session_token(key, stream_id, ttl)` menerima `stream_id` tetapi tidak memasukkannya ke payload JWT (`sub="key:{id}"`, `role="embed"` saja). Dampak: token yang diterbitkan untuk kamera A dapat dipakai ulang pada URL WHEP kamera B bila validator hanya memeriksa signature dan kedaluwarsa.

**A-T4. Opsi `include_playback=False` pada API key diabaikan di jalur external.** `apps/api/app/routers/external.py:367-534`. Nilai `include_playback` disimpan (`admin_keys.py`) tetapi tidak pernah dibaca di `external.py` (nol kemunculan). Dampak: key yang dibuat dengan playback dimatikan tetap bisa mengambil daftar tanggal, segmen, dan berkas rekaman lewat `/api/external/playback*`. Ini bypass batasan cakupan key pihak ketiga.

**A-T5. Token embed yang sah membuat semua endpoint terautentikasi crash 500.** `apps/api/app/core/rbac.py:52`. `_user_from_token` memanggil `int(payload["sub"])` tanpa try/except. Token sesi embed yang diterbitkan sah oleh sistem sendiri punya `sub="key:1"`, sehingga memakainya sebagai Bearer ke endpoint `/api/*` mana pun (misal `/auth/me`) melempar `ValueError` menjadi 500, bukan 401. Hal yang sama berlaku untuk token akses tanpa klaim `sub` (`KeyError`).

## (b) Backend Drive + rekaman + playback + scan + MediaMTX

### Kritis

**B-K1. `recordings_dir` tidak cocok dengan volume Docker: seluruh fitur rekaman/playback mati di jalur deploy Docker.** `apps/api/app/core/config.py:43`, `deploy/docker-compose.yml:85`, `deploy/mediamtx.yml:89`. `recordings_dir` default `"data/recordings"` (relatif terhadap CWD). Container `api` bekerja di `/srv/api`, jadi API membaca `/srv/api/data/recordings` (direktori kosong, bukan volume). Sementara MediaMTX menulis ke `/recordings` (volume `recordings`, sesuai `recordPath: /recordings/%path/...`). `RECORDINGS_DIR` tidak diset di mana pun: tidak di compose, Dockerfile, `deploy/.env.example`, `install.sh`, maupun `update.sh`. Dampak: di deploy Docker resmi, `timeline`/`segments`/`dates` selalu kosong, playback 404, loop retensi dan loop upload Drive memindai direktori kosong (tidak ada yang pernah ter-upload). Satu-satunya yang bekerja adalah perekaman MediaMTX-nya sendiri. Catatan: run native dengan CWD yang kebetulan cocok bisa menutupi bug ini, tapi artefak deploy repo saling bertentangan.

### Tinggi

**B-T1. Playback Drive tidak membaca segmen dari jalur rclone (mode folder-link): rekaman Drive tidak bisa diputar.** `apps/api/app/routers/recordings.py:54` (`_all_segments`), `apps/api/app/services/drive.py:106` (`ensure_folder`), `apps/api/app/services/drive_uploader.py`, `apps/api/app/services/drive_mirror.py`. `_all_segments` hanya menggabung segmen lokal + folder OAuth (`ensure_folder(stream.name)`, folder per nama kamera di bawah root). Sedangkan dua jalur upload folder-link (`drive_uploader` via `rclone copyto` dan `drive_mirror` ke staging) menulis ke folder tautan `drive_folder_id`, yang tidak pernah dibaca playback. Ada tiga jalur upload paralel ke tiga tujuan berbeda, playback hanya mengenal satu. Dampak: segmen yang sudah di-upload ke Drive via rclone tidak muncul di timeline/segments/playback. Setelah retensi lokal menghapus salinan lokal, rekaman praktis hilang dari aplikasi meski file ada di Drive.

**B-T2. Retensi lokal menghapus segmen mode `drive` tanpa memeriksa status upload: satu-satunya salinan bisa hilang.** `apps/api/app/services/recording.py:147` (`apply_retention`). Menghapus semua segmen lokal lebih tua dari `retention_days` untuk semua stream `recording_enabled`, tanpa memeriksa `drive_uploads` atau apakah upload Drive berhasil. Tidak ada guard apa pun. Dampak: bila koneksi Drive putus / upload tertunda melewati masa retensi, rekaman terhapus permanen dari lokal dan tidak ada di Drive (kehilangan data).

**B-T3. `retention_days` > 7 hari diabaikan MediaMTX: rekaman hilang di hari ke-7 walau user menyetel 30 hari.** `apps/api/app/services/stream_paths.py:41` (`main_conf`), `deploy/mediamtx.yml:94`. `main_conf` hanya menyetel `source`/`rtspTransport`/`sourceOnDemand`/`record`; tidak pernah menyetel `recordDeleteAfter` per kamera. Yang berlaku adalah default `recordDeleteAfter: 168h` di `pathDefaults`. Dampak: user menyetel retensi 30 hari, MediaMTX tetap menghapus segmen di hari ke-7 (kehilangan data diam-diam). Sebaliknya retensi < 7 hari hanya ditopang loop API harian, bukan MediaMTX.

**B-T4. rclone tidak ada di image API dan tidak ada mount staging di compose: mode folder-link mati total di deploy Docker.** `apps/api/Dockerfile` (hanya menginstal `ffmpeg`), `deploy/docker-compose.yml` (tidak ada volume untuk staging/`data`), `apps/api/app/services/gdrive_rclone.py:36` (`find_rclone`), `:24` (`_data_dir`). `Dockerfile` tidak menginstal rclone; compose tidak menyediakan mount untuk `gdrive_record_path`; `.rclone.conf` ditulis CWD-relatif (`data/.rclone.conf`, tidak di-volume) sehingga token hilang saat container dibuat ulang. Dokumen `docs/GOOGLE-DRIVE.md` justru mengasumsikan rclone terinstal di host + `rclone mount` systemd, yang tidak bisa dijangkau container API. Dampak: di deploy Docker, tombol Hubungkan, verifikasi folder, `upload_segment`, dan mirror semuanya gagal (`RuntimeError: rclone tidak ditemukan`). Mode folder-link, yang merupakan jalur Drive utama saat ini, tidak berfungsi di jalur deploy resmi.

**B-T5. Segmen Drive terbaru berdurasi 0 dan tidak bisa diputar.** `apps/api/app/services/recording.py:64` (`_assign_ends`), `apps/api/app/routers/recordings.py:54`. Untuk segmen terakhir, `end` diambil dari `mtime` file. Segmen Drive punya `path=""`, `os.path.getmtime("")` selalu `OSError`, sehingga `end = start`: `duration_sec = 0` di `/segments`, dan `_containing` (`start <= at < end`) tidak pernah cocok. Dampak: segmen Drive terbaru (kasus umum di mode `drive` atau setelah retensi lokal) tercantum tapi tidak bisa diputar lewat `playback-url`, `stream`, `file`, maupun `next-playable` (404).

**B-T6. Volume recordings di-mount read-only di container API: retensi lokal tidak pernah bisa menghapus di Docker.** `deploy/docker-compose.yml:85` (`recordings:/recordings:ro`), `apps/api/app/services/recording.py:147`. `apply_retention` menghapus via `os.remove`, yang selalu gagal di mount `:ro` (hanya tercatat sebagai warning). Dampak: kalaupun B-K1 diperbaiki dengan menyetel `RECORDINGS_DIR=/recordings`, retensi API tetap tidak jalan; pembersihan hanya mengandalkan `recordDeleteAfter` MediaMTX 168 jam. (Terkait B-K1 tapi cacat independen.)

### Sedang

**B-S1. Playback segmen Drive tanpa dukungan HTTP Range: seek tidak berfungsi.** `apps/api/app/routers/recordings.py:111` (`_serve_segment`). Segmen lokal dilayani `FileResponse` (Starlette 1.10 mendukung Range), tapi segmen Drive dilayani `StreamingResponse` polos tanpa `Accept-Ranges`/`Content-Length` dan mengabaikan header `Range`. Dampak: pemutar video tidak bisa melompat (seek) pada rekaman yang diambil dari Drive; hanya putar progresif dari awal.

**B-S2. `playback-url` fallback hanya memeriksa segmen lokal: 404 walau Drive punya segmen berikutnya.** `apps/api/app/routers/recordings.py:283`. Bila tidak ada segmen yang memuat waktu yang diminta, fallback memakai `find_next_playable` (lokal saja). Endpoint `next-playable` (`:304`) sudah menangani Drive, jadi dua endpoint kontraknya inkonsisten. Dampak: pemutar yang memakai `playback-url` gagal melompat ke rekaman Drive berikutnya.

## Temuan yang sudah diketahui sebelumnya (dikonfirmasi masih ada)

Temuan di bawah ini sudah diketahui dari analisa sebelumnya dan dikonfirmasi ulang oleh para analis masih ada di HEAD `7869b6e`. Bukan temuan baru.

1. **H1, scan subnet /24 bisa hang.** `apps/api/app/routers/admin_scan.py:113` (`scan_subnet`): `asyncio.gather` atas maks. 256 host, semafor 4, timeout 45 detik/host, tanpa timeout global, worst-case ~48 menit untuk satu request `/24`. Catatan tambahan: daftar host dimaterialisasi seluruhnya (`[str(h) for h in network.hosts()]`) SEBELUM pengecekan batas 256, jadi CIDR dengan prefix sangat kecil (mis. IPv6 `/64`) akan hang/OOM dan memblokir event loop sebelum batas sempat berlaku.
2. **H2, `ensure_path` PATCH/reload sub path tiap 60 detik.** `apps/api/app/main.py:55` (`_mediamtx_sync_loop`, tiap 60 detik) memanggil `register_stream` lalu `ensure_path` (`apps/api/app/services/mediamtx.py:86`), yang melakukan GET lalu PATCH tiap path yang berbeda.
3. **M1, IP staging hardcoded di `deploy/mediamtx.yml`.** `deploy/mediamtx.yml:39`: `webrtcAdditionalHosts: [103.210.52.66]`.
4. **M3, kredensial kamera terlihat di `ps`.** `apps/api/app/services/rtsp_discovery.py` (`_run_ffprobe`): URL RTSP lengkap beserta kredensial dilewatkan sebagai argv `ffprobe`, sehingga terlihat di `ps`.
5. **RBAC backend Iklan/API Key/Scanner/Penyimpanan masih `require_roles("admin")`, bukan `super_admin`.** Terkonfirmasi di `admin_ads.py:26`, `admin_keys.py:22`, `admin_scan.py:21`, `admin_drive.py:38`. Lihat juga E-K1: redirect frontend yang seharusnya menegakkan pembatasan ini ternyata dead code, sehingga celah ini bisa dieksploitasi penuh lewat URL.
6. **`list_users` masih scope by `parent_admin_id`, bukan `admin_group`.** Terkonfirmasi di `apps/api/app/routers/admin_users.py:131-135`.

Yang dikonfirmasi masih sesuai desain (bukan bug): admin biasa tidak boleh CRUD kamera (superadmin only, `admin_streams.py:94` dan dependensi tiap endpoint); guest tanpa password dan default nonaktif (`auth.py:122-157`, `_guest_login_enabled` memakai baris guest di DB, fallback env `GUEST_ENABLED`); endpoint `/api/external` memakai 403 untuk error kunci/kamera (penyimpangan hanya 400/404 di jalur playback, lihat A-S3).
